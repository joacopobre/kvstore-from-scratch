kvstore

What it is

kvstore is a key-value database that I wrote from scratch in Python. You store a value under a key (SET), read it back (GET) and remove it (DELETE), and the data survives crashes and restarts.

I built it to understand how storage engines work underneath, so the store uses only Python's standard library and no database libraries (the tests use pytest). I focused on the parts that make an engine trustworthy:

  • Durability. Every write goes into a write-ahead log on disk before it is acknowledged, so a write the store has confirmed is not lost if the process dies.
  • Crash safety. The log is append-only, and a record that was only half written when the machine went down is detected when the store restarts and cut off the end of the log.
  • Speed. Recent writes live in an in-memory table, so reads are fast. When the table grows past a size limit, it is flushed to sorted files on disk.
  • Tested against crashes. Tests kill a real store process at chosen points in a flush and in a compaction, then reopen the data and check that everything written before the crash reads back correctly.

Around the store there is a binary protocol over TCP that I designed, a Python client, a TypeScript client, and a small Node server that exposes the store over HTTP for this website. The Console tab talks to the real database, so you can try it yourself.

Try it

Open the Console tab. Choose an operation, type a key (and a value for SET) and press the button. The result appears underneath in plain words, and "Raw response" shows exactly what the server sent back.

A good first run: SET name with the value hello, GET name, DELETE name, then GET name again to see the "not found" case.

Some things to know. The demo data is shared by every visitor and is wiped every day at 04:00 UTC, so please don't store anything private. Keys can be up to 128 bytes and values up to 1,024 bytes, and each visitor is limited to 60 requests per minute.

How a request travels

Here is what happens when you run a SET:

  1. The browser sends POST /api/set with the key and the value as JSON.
  2. Caddy, the reverse proxy, ends the HTTPS connection (using a certificate from Let's Encrypt) and passes the request to the Node app over a private network. It is the only part of the system that can be reached from the internet.
  3. The Node app checks the request (key, value and body sizes) and applies the rate limits. Then it opens a TCP connection to the store and sends one binary message, using my TypeScript client.
  4. The store reads the message, appends the record to its write-ahead log, waits for it to reach the disk, updates the in-memory table and replies with a status byte.
  5. The Node app turns the status byte into an HTTP status and a JSON body, and the Console shows the friendly message and the raw response.

A GET follows the same path: the store looks the key up and the value comes back in the response.

The storage engine

Writing. Each SET or DELETE is first appended to the write-ahead log, a file that is only ever added to. The store waits until the operating system confirms the bytes are on disk (fsync) before it replies, and that wait is what makes an acknowledged write durable. It happens on every write, one at a time, with no batching.

Surviving a crash. Each record in the log starts with its length, so the store can tell a complete record from one that was cut short. On startup the engine replays the log to rebuild what was in memory. It stops at the first incomplete record and cuts the log off at that point. There are no checksums, so this catches a record that was cut short, but not one whose bytes were damaged.

Memory and disk. The in-memory table (the memtable) holds the latest value for each key. When it passes a size limit (4 MB by default), it is written out as an immutable sorted file (an SSTable). The file is written under a temporary name, synced to disk and renamed into place, and only then is the log deleted. Reads check the memtable first, then the sorted files from newest to oldest, because a newer value hides an older one.

Deletes. A delete is recorded as a marker called a tombstone, first in the log and the memtable and later in the sorted files. A read stops at the first place that mentions the key, so a tombstone hides any older value under it.

Compaction. Over time sorted files pile up. When there are four of them, the engine merges them all into one new file, keeping only the newest value for each key and dropping deleted keys. Then it deletes the old files, oldest first, so that a crash part-way through cannot bring a deleted key back.

Testing. The worst bugs in a storage engine happen when the process dies at the wrong moment, so the tests inject crashes at those moments: after writes that have not been flushed yet, at three points in a flush (before the new file is renamed into place, after the rename, and after the log is deleted) and at four points in a compaction (after the merged file is written, and after each of the three old files is deleted). Each test kills a real child process at that point, reopens the store and checks that the data written before the crash reads back correctly. That is eight crash points in total.

The wire protocol

Programs talk to the store over TCP with a small binary protocol that I designed. TCP delivers a stream of bytes with no message boundaries, so every message starts with its length: 

frame     [4 bytes: payload length, big-endian] [payload]
request   [1 byte: command] [4 bytes: key length] [key] [value]
response  [1 byte: status] [body]

The commands are SET, GET and DELETE, and the statuses are OK, NOT_FOUND and ERROR. The server rejects messages over 16 MB, so a bad length can't make it buffer unlimited data.

A message can arrive split across several network chunks, or several messages can arrive in one chunk. So the clients keep incoming bytes in a buffer and decode only when a whole frame is there. The TypeScript client does this with a small byte queue and a socket reader that hands out exactly the number of bytes asked for.

Deployment

The site runs on a single Linux server (a DigitalOcean VPS) with Docker Compose. There are three containers: the store, the Node app and Caddy. Only Caddy publishes ports (80 and 443). The store and the Node app can be reached only inside Compose's private network. The store's data lives in a named volume, so it survives container restarts and reboots, and the containers restart on their own. I tested that by rebooting the server.

The server is locked down: a non-root user, SSH keys only (no passwords and no root login), and a firewall that lets only SSH, HTTP and HTTPS in from outside. Caddy gets and renews the HTTPS certificate automatically.

Because anyone can write to the demo, I limited what it can be used for: size limits on keys, values and request bodies; a rate limit per visitor (60 requests a minute); a global budget (2,000 requests to the store an hour) after which the demo says it is at capacity; and a scheduled job that wipes all the data every day at 04:00 UTC.

Limitations

  • The store has no authentication. It is meant to run on a private network, and in this deployment only the Node app can reach it.
  • The rate limit and the request budget are kept in the Node app's memory, so they reset when it restarts.
  • The demo data is shared between all visitors and wiped daily.
  • The Console sends and shows text only, while the protocol itself carries raw bytes.
  • It is a single node with no replication, so if the server's disk is lost, so is the data.
  • The engine uses one lock for everything, so it handles one operation at a time, and a flush or a compaction makes every client wait.
